## Solución implementada y verificada

- Backend PHP 8.2 con capas Controller / Service / Repository, MariaDB mediante PDO y consultas preparadas, API REST y autenticación. `TelemetryService` comparte validación, idempotencia y persistencia entre HTTP y un suscriptor MQTT independiente. Apache sirve HTTPS; Mosquitto usa MQTT QoS 1/TLS para la LAN. D1 seguro de loopback usa `127.0.0.1:1884`; D2 para ESP32 #3 usa TLS en 8883. El listener 1883 observado históricamente no se declaró seguro.
- Hay tres ESP32 físicos con identidades y credenciales propias. #1 transmite por HTTPS con PIR físico, relé y LED; #2 transmite por HTTPS con PIR simulado y RSSI real; #3 transmite por MQTT/TLS con PIR simulado y RSSI real. El docente autorizó los PIR simulados de #2/#3; declararlos como tales. Arquitectura de demostración: hotspot Android de 2,4 GHz → laptop con Apache, PHP, MariaDB y Mosquitto → tres ESP32 por Wi-Fi. USB se usó para alimentación y captura serie, no para telemetría. El escritorio queda para desarrollo.
- Idempotencia por identidad y secuencia, incluso tras reinicio; el mensaje pendiente y su secuencia se persisten para reintentos sin cambiar el contenido. `node_id` se vincula a la credencial; `timestamp` es Unix UTC válido o `null` y `received_at` lo asigna el servidor. No borrar NVS ni resembrar la base. QoS 1/PUBACK acredita recepción del broker, no necesariamente commit en MariaDB; no prometer pérdida cero ante cortes bruscos.
- HTTPS exige CA y nombre de servidor verificados; preservar TLS, SAN, autenticación y ACL. La conexión TCP por IP conserva nombre TLS/SNI. #1 utiliza PIR en GPIO27 y relé en GPIO26 mediante BC548, con LED de baja tensión y retención funcional aproximada de 10 s. La calibración y caracterización temporal cuantitativa del PIR, así como detalles del cableado final del LED, no están acreditados. No inferirlos del Lab1 histórico.
- Las pruebas locales históricas en laptop cubrieron telemetría HTTP, los otros cuatro endpoints REST, autenticación y ACL MQTT, ingesta por suscriptor, idempotencia y concurrencia (cuatro procesos, una inserción). El menú `scripts/demo.ps1` (opciones 1–7) se verificó históricamente en escritorio y laptop; la corrección PUBACK 0/16 está conservada. Estas ejecuciones anteriores no prueban por sí mismas el arranque desde la nueva raíz. La guía oficial exige T01–T05; T06–T08 fueron planificación, no requisitos oficiales. No ejecutar de nuevo `schema.sql` ni `seed.sql` en la base existente.
